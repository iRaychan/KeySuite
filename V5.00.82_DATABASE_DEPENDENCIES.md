# Database dependency — approval required

Bug 001 is **blocked for live secure-history Full access** until an approved database change is applied and verified. No production SQL was executed for this release.

Read-only inspection of the live KeySuite database confirmed that `keysuite_list_quotations_v42919(text)` checks the literal role `owner` and returns only the authenticated creator's records for every other role. Both quotation tables have RLS enabled and no direct SELECT policies; the application uses the existing SECURITY DEFINER history gateway. Adding a broad table policy would not repair this RPC's internal owner-only filter.

The proposed `proposals/V5.00.82_QUOTATION_VIEW_APPROVAL_REQUIRED.sql` makes that primary gateway read the existing `ks_role_permissions` configuration through `keysuite_permission_level`. Full/all returns company quotations, Own (including legacy Assigned) returns creator-owned quotations, and None returns none. Company boundaries, authentication and existing execution grants remain intact. It does not modify customer access, create/save, deletion, sealing or approval rights.

The proposal passes an in-memory PostgreSQL (PGlite) test with two creators, Full/Own/None, inactive accounts, company isolation, archive/current deduplication and execution grants. Authentication helper interfaces were simulated in that test; it is not a live Supabase authentication/RLS verification. Before approval/application: verify the change with real authenticated isolated accounts, current authorization helpers, save and deletion separation. Review legacy public list/get quotation RPC grants as well: the primary proposal alone does not make legacy endpoints a complete None authorization boundary. No existing grants are revoked automatically in this package.

Approval requested for a separately reviewed database authorization repair. Until then, the frontend fix cannot retrieve quotations the server withholds; do not treat Bug 001 as fully resolved in production.

Customer payment terms use the existing unrestricted `ks_customers.payment_terms` TEXT field. Ordinary credit terms retain their legacy encoding; special options use a versioned JSON text value to preserve days, PDC, option and custom wording together. No new columns or migration are required. All application displays decode through the shared payment-terms codec. Older application versions will not understand special-option JSON values; upgrade all clients before editing special terms, and export/backup customers before any downgrade. Historical quotation `payment` strings remain snapshots.
