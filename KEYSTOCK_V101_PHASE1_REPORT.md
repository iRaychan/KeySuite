Physical On Hand totals active opening balances. Assemblable Stock uses quantity less the largest recorded critical shortage within each configuration and location, then totals the result for the model. Reserved Stock and Available to Promise show a dash because there is no reservation ledger in Phase 1. A model total does not authorize substitution between configurations.

An Owner can configure the six stock permissions in the existing role matrix. They default to full for Owner/Admin and none for other roles. The server enforces these permissions independently of Edit Mode and hold gestures. Dropdown setup, mapping saves and opening balances retain their existing Owner/Admin requirement. The time holds guard the interactive controls. Purchase costs retain their separate server permission, and the supplier table has row-level security with no direct grants to browser roles.

The database test runs the dated V1.00 migration, creates legacy rows, runs the V1.01 migration and verifies retained data. The browser uses that isolated fixture. The test covers supplier and location reload and simulated auth contexts. Live sign-in and post-deployment acceptance remain to be checked. The production read-only inspection found 11 private KeyStock tables with row-level security enabled and zero direct row policies, consistent with the existing command API model.

Existing quotation unit and manual item tests passed, including save/reopen, revision/clone and PDF preview/download byte identity. The existing Assembly/System pricing test passed. Product, Selection, Curve, Pricing, Pricelist, Quotation, PDF, Assembly and KeyHQ source logic were compared with the exact baseline. These checks do not cover every hosted interaction.

## Deployment and rollback

1. Confirm the target already has the V1.00 database migration. Back up the database and capture the current Git commit. Compare the current repository with V5.00.51 before overlaying the upgrade at the repository root. Reconcile any intervening changes.
2. Test the upgrade in a non-production Supabase project with representative V1.00 data. After production approval, apply only `supabase/migrations/20261108033326_v50052_keystock_v101.sql` once. It runs in a transaction. Keep the historical migration files in the repository. Do not run a blanket migration push where the locally named V1.00 file and the hosted V1.00 migration history have different timestamps.
3. Verify the supplier table, existing opening balance IDs and totals, mapping retirement field, and tenant and cost permissions. Check V1.01 under an Owner and a user without costing access.
4. Stage the overlay in Git and run `python3 tools/build_pages.py`. Publish through the existing Pages workflow after approval. Verify that the intended commit's Actions build and deployment succeeded. Refresh the custom domain, confirm V5.00.52 and KeyStock V1.01, then check an existing model, mapping, opening balance and quotation PDF.
5. For a site rollback, redeploy the exact V5.00.51 application through Pages and keep the additive migration in place. The V1.00 site lacks the new supplier and retirement controls, so keep KeyStock maintenance paused until the V1.01 site is restored. If KeyStock must be disabled, revoke execution of `public.keysuite_stock_v100(text,jsonb)` from `authenticated`. Regrant it to restore access. The schema, balances, supplier links and audit entries stay in place. Any database point-in-time restore needs a separate review of stock changes made after the migration.
