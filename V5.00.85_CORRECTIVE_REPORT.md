## Bug 001: why VEC 32-3 worked while 150-2-1 did not

The C4 hydraulic records both belong to the shared CHC source family; neither has an independent VEC/B.G.Reich brand field. The live configured VEC mapping is CHC_G1 / CHC -> VMS for both models. Their technical differences are legitimate: CHC 32-3 has 5.5 kW / 7.5 HP and DN65 connection, while CHC 150-2-1 has 22 kW / 30 HP and DN125 connection. Those records are unchanged.

The read-only price comparison confirms a routing difference: `G1:CHC 32-3` has populated source prices, while `G1:CHC 150-2-1` has no positive source price (MYR null, RMB 0, USD null). The latter enters the manual-price offer. Prices were inspected, not repaired or changed.

In `app.js`, the CHC `KEYSUITE_ADD_SELECTION` receiver originally built `masterDescription` with a literal B.G.Reich prefix and a source-derived model before asking for a manual price. A Curve payload whose display model was already aliased could therefore produce B.G.Reich / VMS, matching the screenshot; a raw CHC payload produced B.G.Reich / CHC.

The decisive incorrect transformation was `manual-price-v50011.js::offer`, form submit: it added `descriptionManuallyEdited:true` even though the user edited only the price. `commercial-identity.js::stamp` and `applyToRow` correctly respect genuine user edits, so they preserved that erroneous generated text. This explains why tests of automatically priced items passed while the unpriced item still failed.

The repair constructs the generated model and description from the captured commercial snapshot before either pricing branch. `offer` snapshots and clones the item before opening the asynchronous dialog and preserves the existing description-edit flag instead of setting one for a price edit. The actual dialog is now tested through submit, including navigation to another brand while it is open.

## Bug 002: why intentional brandless VMS became B.G.Reich / CHC

The live `-` brand has its own brand ID, an active CHC_G1 / CHC -> VMS mapping and a VMS C4 navigation label. The CHC 10-4 and CHC 90-2 source price records are populated. An intentionally brandless selection is valid; absence of a printed brand prefix does not mean “choose the master brand.”

Two conflicting resolver inputs were confirmed in the original source:

1. `commercial-identity.js::forItem` treated `pricingSource.v391_brand_id` / `v391_brand_name` as explicit commercial identity. That bypassed the selected brand context. A legacy item under `-` with a shared B.G.Reich pricing source first became B.G.Reich / CHC here. The new baseline comparison records this exact failure for VMS 10-4 and VMS 90-2.
2. `commercial-identity.js::captureSelection` resolved the selected brand correctly, then replaced its name with `payload.keysuite_brand_name`. A stale catalogue B.G.Reich name could thus overwrite the selected configured brand. A separate baseline negative test confirms this overwrite.

`v40001-multibrand.js::stampRowBrand` also permitted a master-brand fallback for an unresolved ID. The revised function uses an already captured item snapshot and no longer substitutes the master brand when lookup fails.

The shared resolver now uses the item's commercial snapshot, explicit selling identity or valid selection context. Pricing metadata remains a source for costs and engineering context, not a fallback commercial brand. Empty and `-` printed brands remain intentionally empty. Invalid family/model presentation pins are rejected before their group is used. No model-specific exceptions or new broad text replacements were added.
